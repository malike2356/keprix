Contributing

keprix welcomes contributions. Read this before opening a pull request.

Before you start.

For bug fixes and small improvements: open a pull request directly. Include the issue number if one exists.

For new features or architectural changes: open a GitHub Discussion first. Describe what you want to build and why. Maintainers will confirm scope and approach before you invest time writing code. This prevents rejected pull requests.

Development setup.

$ git clone https://github.com/malike2356/keprix
$ cd keprix
$ python -m venv .venv && source .venv/bin/activate
$ pip install -e ".[dev]"
$ cp .env.example .env # fill in at least one LLM key
$ docker compose up -d postgres redis
$ keprix --help

Code style

Python: Black formatting, Ruff linting. Run make lint before committing. The CI gate will reject unformatted code.

Tests

pytest. Unit tests in tests/unit/. Integration tests in tests/integration/ (require Docker). Run make test. New features need test coverage.

Type annotations

All public functions must have type annotations. mypy strict mode enforced in CI. Do not use Any without a comment explaining why.

Commit messages

Conventional Commits format: feat:, fix:, docs:, refactor:, test:. Short subject, no trailing period. Body if the change is non-obvious.

Pull request size

Keep PRs focused on one thing. Large refactors split into logical steps. PRs over 600 lines of non-generated diff will be asked to split.

Licence requirements

keprix is MIT. Any dependency you add must have a compatible licence (MIT, Apache 2.0, BSD). AGPL and GPL dependencies are not permitted - they poison the MIT licence for downstream users.

What to work on.

Good first issues are labelled good first issue on GitHub. These are scoped, documented, and have a clear acceptance criteria.

Help wanted issues are labelled help wanted. These are more open-ended and may require design discussion before implementation.
