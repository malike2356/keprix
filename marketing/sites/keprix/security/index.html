Security

How to report a vulnerability in keprix and what to expect.

Reporting a vulnerability.

Do not open a public GitHub issue for a security vulnerability. Public issues expose the vulnerability to all users before a fix is available.

Use GitHub's private vulnerability reporting: go to the keprix repository, click Security, then click "Report a vulnerability." This creates a private disclosure visible only to the maintainers.

Include: the vulnerability type, the affected component, steps to reproduce, and the potential impact. The more detail you provide, the faster we can triage.

Response timeline.

24h

Acknowledgement

We will acknowledge receipt of the report within 24 hours and confirm whether it is in scope.

7d

Initial assessment

We will triage the severity and confirm a fix timeline within 7 days. We will keep you updated if assessment takes longer.

90d

Disclosure

We aim to fix and publicly disclose within 90 days of the initial report. We will coordinate the disclosure date with the reporter.

Scope.

In scope

  • keprix agent kernel and tool loop
  • Mutation engine approval gate bypass
  • Tool sandbox escape
  • Hub authentication bypass
  • Memory layer data leakage
  • Remote code execution via keprix

Out of scope

  • Vulnerabilities in the LLM providers you configure
  • Vulnerabilities in Labyrinth Scout (report to Scout)
  • Social engineering or phishing
  • Physical access attacks
  • Denial of service on your own instance
  • Vulnerabilities requiring admin credentials already in attacker hands

Security hardening notes.

keprix is self-hosted. You control the network boundary. The main attack surface is the hub API. Recommendations: put the hub behind an authenticated reverse proxy, do not expose port 3333 to the public internet, use strong API keys, and keep the Docker socket inaccessible from within the tool sandbox.

See the security hardening section in the README for the full checklist.
