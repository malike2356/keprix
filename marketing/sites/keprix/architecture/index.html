system design

Architecture

keprix is a layered AI agent OS. Each layer has a clear boundary and can be extended independently.

System layers.

keprix is organised as five concentric layers. Requests enter from the outside (channels) and travel inward to the agent kernel. Responses travel outward. The Mutation engine sits adjacent to the kernel, proposing and (after approval) installing new tools without restarting the runtime.

Layer 5: Channel adapters (Telegram, Discord, REST, browser)
Layer 4: Hub - session management, routing, auth
Layer 3: Memory - short-term context + long-term vector store
Layer 2: Agent kernel - tool loop, LLM routing, playbook engine
Layer 1: Tool sandbox - Python execution, approval gate, Mutation engine
External: Optional Scout governance connector (Labyrinth Scout)

Agent kernel

The agent kernel manages the function-call loop. It receives a task, selects from the registered tool set, calls the LLM with the tool schema, executes the chosen tool, and iterates until the task resolves or requires human input.

LLM routing is configurable per-task. One task can use Anthropic Claude for reasoning and Mistral for summarisation. The kernel does not care which provider is behind each call.

Tool sandbox

All tool execution happens inside Docker. The sandbox has no network access unless the tool explicitly requests it. File system access is scoped to a per-session scratch volume.

The Mutation engine writes candidate tools here first. If the sandbox run succeeds, the tool surfaces for approval. If it fails, the error is reported and the mutation attempt is discarded.

Memory layer

Short-term memory is the conversation window. Long-term memory is a vector store backed by PostgreSQL with the pgvector extension. Entities (people, organisations, tasks) are extracted from conversations and stored in a structured memory graph.

Retrieval-augmented generation pulls relevant long-term context into the kernel prompt before each LLM call.

Hub

The hub manages sessions, routes incoming messages from channel adapters to the correct agent context, and enforces per-user rate limits. It also exposes the REST API used by the browser interface and programmatic clients.

Authentication is configurable: API key, OAuth, or single-user local mode.

Channel adapters

Adapters normalise input from Telegram, Discord, the REST API, and the web UI into a common message format before passing it to the hub. Adding a new channel means writing one adapter that satisfies the channel interface.

Scout connector (optional)

Labyrinth Scout attaches as an optional sidecar. It observes all tool calls and LLM completions, writes a tamper-evident audit log, and enforces operator-defined policies (allowed tool classes, budget caps, restricted topics).

keprix works without Scout. Scout is a paid external service.

Infrastructure requirements.

Min

Single machine

2 vCPU, 4 GB RAM. keprix + PostgreSQL + Redis on one host. Suitable for one user or a small team. Tested on a $6/month VPS.

Mid

Separated data layer

4 vCPU, 8 GB RAM. keprix runtime on one host, managed PostgreSQL and Redis elsewhere. Standard team configuration.

HA

Kubernetes deployment

Helm chart provided. keprix hub as a deployment, tool sandbox as a DaemonSet. Horizontal scaling on the hub layer only.

Data stays on your infrastructure.

Conversations, memory, task history, and tool outputs are stored in PostgreSQL and Redis on your server. Nothing is sent to Carina, Verlox, or any third party. The only outbound traffic is the LLM API calls you configure.
